# Performance

1. [hard] Missing deadline on outbound I/O — `pkg/dbsource/updater.go:157` — `Stop` now joins the loop goroutine (`u.running.Wait()`, under `u.mu`) but nothing cancels the GET that goroutine may be inside. `tick` → `UpdateIfNeeded` → `Update` → `dbutils.HTTPGet`, whose only bound is `HTTPGetTimeout = 30 * time.Minute` plus an unpack/copy of up to `HTTPGetMaxBytes = 6 GB`; `close(stop)` does not touch the in-flight request. That wait is on the plugin-construction path: `pkg/reclaim/table.go:305` calls `sleepValue` with the slot parked in `slotBusy`, `sleepValue` reaches `BIN.Sleep` (`pkg/dbwrappers/bin.go:343`) and `MMDB.Sleep` (`pkg/dbwrappers/mmdb.go:180`), and the next `Open` for that key blocks on `<-ready` at `pkg/reclaim/table.go:198`. So a Traefik dynamic-config reload that re-opens a key whose last holder just went away stalls for as long as that download runs. On `origin/master` `Stop` only closed the channel and ran from a lifetime watcher, so no `Open` could ever wait on it — the coupling is new in this diff. What grows: the stall grows with database size and network speed up to the 30-minute ceiling, and it is one stall per reload that lands in the sleep window.
   → Give the download a context that `Stop` cancels (thread `stop` / a `context.Context` into `HTTPGet` via `http.NewRequestWithContext`) so the join returns promptly, or bound the join (`Wait` with a short timeout and let the orphaned tick discard its result — `tick` already re-checks `stopped(stop)` before the callback).
   Status: open
   Argument: none.
2. [judgement] Hot-path full scan or compile — `pkg/dbsource/updater.go:99` — `Updater.Start` runs an immediate `tick` before entering the ticker loop, and `Wake` now calls `startUpdate` on every reclaim (`pkg/dbwrappers/bin.go:349`, `pkg/dbwrappers/mmdb.go:186`). Work that used to run once per incarnation now runs once per reclaim: a `Latest` directory glob every time, and a full GET whenever `Latest` is older than `MinAge`. The reclaim table exists to make a reload cheap, so this puts back per-reload cost on the path it is meant to remove. What grows: number of dynamic-config reloads. The `update-<key>.lock` file only dedupes downloads that overlap in time, and `MinAge` stops the GET only when a fetch can actually produce a newer dated file — the "not newer than the one already available" branch in `Update` re-downloads and discards.
   → Start the ticker without the immediate tick when the loop is being restarted after a sleep, or gate the immediate tick on time since the last check.
   Status: open
   Argument: none.
3. [judgement] Hot-path lock contention (no matching checklist row; recorded because the conductor named it) — `pkg/dbwrappers/bin.go:270` — `LookupRecord` takes `w.mu.RLock()` on every request. The window is two field loads and the lock is released before `db.Get_all`, and the only writers are hot swap (~1/24h), `Sleep`, `Wake`, and `Close`, so there is no reader/writer blocking to speak of; what remains is the shared `readerCount` word an `RWMutex` bounces between cores. `MMDB.Lookup` (`pkg/dbwrappers/mmdb.go:163`) already did exactly this on `origin/master`, so the diff follows the tree's own idiom rather than inventing a cost. What grows: concurrent in-flight requests times cores. Recording, not asking for a change.
   → If per-request lookup ever measures as contended, hold the live handle in an `atomic.Pointer[ip2loc.DB]` and keep `w.mu` for the cold multi-field swap. Do not change this without a measurement.

   Argument: none.
